## 背景（Context）

当前工程仍是 Android Studio 模板：单 `:app` 模块、Kotlin + XML 布局、AppCompat、Material Components、Navigation 和 ViewBinding。MVP 需要在这个基础上提供疾控现场可演示的主流程：用户一键测量，App 本地采集手机信号，估算温湿度，采集或修正点位名称，本地保存报告并生成待复制结果。

本设计按技术方案给出的声学、热特征和融合方式推进，但把算法实现放在可替换边界内，避免 UI、存储、填报逻辑直接依赖某个模型细节。音频隐私、权限拒绝、设备输入缺失和本地报告可靠保存是核心约束。

## 目标 / 非目标（Goals / Non-Goals）

**目标：**

- 将模板页替换为 MVP 主流程：测量、结果确认、点位录入/修正、本地保存和复制结果。
- 提供清晰的测量状态模型，包括准备中、采集中、计算中、成功、降级成功、失败和需重测。
- 按技术方案接入声学估算、热特征估算和融合质控，输出温度、湿度、置信度、来源和质控说明。
- 权限拒绝或设备输入缺失时，App 进入可解释的降级路径，而不是直接崩溃或卡住。
- 原始音频只在测量期间存在于内存，计算完成后清理，不写入本地存储，不上传。
- 提供报告草稿/历史记录的加密本地保存，并生成格式稳定的待复制结果。

**非目标：**

- 不在 MVP 内完成生产级模型训练、机型库后台更新、远程模型下发或正式计量认证。
- 不在 MVP 阶段对接官方 API、网页表单或第三方 App 自动填充。
- 不在本阶段迁移到 Jetpack Compose 或多模块架构。
- 不在本阶段保存或回放原始音频用于调试。

## 决策（Decisions）

### 1. 沿用单模块 XML/ViewBinding 架构

继续使用现有 `:app`、XML 布局、Navigation 和 ViewBinding。新增代码按包拆分，不先引入 Compose 或多模块。

备选方案是重建 Compose UI 或拆分多模块，但 MVP 的首要目标是跑通产品闭环；当前工程体量小，单模块分包足够支撑迭代，也减少构建和迁移成本。

建议包结构：

- `ui`：测量首页、结果确认、报告历史、复制结果和状态展示。
- `measurement`：测量会话、音频采集、热特征采集、融合、质控。
- `reporting`：报告模型、复制文本生成、报告状态规则。
- `storage`：本地报告记录、加密、状态持久化。
- `privacy`：权限请求、隐私文案、音频清理约束。
- `model`：跨层数据结构，如 `MeasurementResult`、`ReportDraft`、`ReportStatus`。

### 2. 用可替换估算器封装声学和热特征算法

测量层暴露统一接口，例如声学估算器输入音频采样、机型参数和气压，输出 `Estimate`；热特征估算器输入电池温度、CPU 温度和负载，输出 `Estimate`；融合层只依赖估算结果和置信度。

这样可以先接入技术方案中的实现或占位模型，后续替换 JNI、轻量模型、机型库或校准参数时，不影响 UI、填报和存储。

备选方案是直接把算法写进 Fragment 或单个 Service。那会让权限、音频生命周期、错误处理和 UI 状态纠缠在一起，不利于验证和替换。

### 3. 测量流程显式建模为状态机

测量会话使用显式状态，而不是零散布尔值：

```
Idle
  │
  ▼
CheckingPermission
  │ granted              │ denied
  ▼                      ▼
CollectingSignals     ThermalOnlyDelay
  │                      │
  ▼                      ▼
Estimating ─────────▶ QualityCheck
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
       Success                    NeedsRetry / Failed
```

状态机让 UI 可以稳定展示“正在采集”“60 秒热特征模式”“信号不佳请重测”等提示，也方便单元测试覆盖失败路径。

### 4. 填报采用“报告草稿 + 本地仓库 + 待复制文本”

测量完成后先生成 `ReportDraft`，用户确认点位和数值后保存为本地报告。App 根据报告生成待复制文本，用户可复制到疾控填报系统中手动提交。报告状态至少包含草稿、已保存、已复制和已作废。

复制文本生成使用明确模板，包含点位、温度、湿度、测量时间、置信度/质控提示。后续如果要接入 API、网页或第三方 App 表单，可以在 `reporting` 边界下新增提交客户端，而不改变测量和本地报告模型。

备选方案是首版就接入 API 或自动填表。该方式更贴近最终自动化，但目前接口未知、合规边界未确定，容易把 MVP 卡在外部系统集成上；先生成待复制结果可以更快验证测量和现场使用流程。

### 5. 本地报告用平台本地存储加字段级加密

MVP 保存报告草稿/历史记录、复制状态、创建时间和更新时间。原始音频不持久化。首版使用平台 `SharedPreferences` 保存加密后的报告记录，使用 Android Keystore 管理密钥，对报告敏感字段做字段级加密；这样可以减少依赖并更快完成本地闭环。

备选方案是引入 SQLite、Room、SQLCipher 或完整同步框架。它们更强，但首版会增加依赖和迁移复杂度；如果后续报告历史、查询和同步能力复杂化，再升级存储实现。

### 6. 权限和隐私作为产品流程的一部分

首次测量前展示麦克风权限用途说明；用户拒绝麦克风时进入热特征降级模式，并明确提示预计耗时和置信度限制。首版不依赖网络提交，因此网络权限和联网状态不作为 MVP 主流程前置条件。

语音识别只用于点位名称采集，且必须允许手动修正。若使用系统语音识别能力，需要在隐私说明中区分“温湿度测量音频本地处理”和“点位语音识别可能依赖系统能力”的边界；若产品要求完全本地识别，后续需要引入本地 ASR 方案。

## 风险 / 权衡（Risks / Trade-offs）

- 设备不支持双麦立体声采集或气压输入 → 测量层返回输入缺失原因，自动降级到热特征模式或提示重测。
- `/sys` CPU 温度节点不可读或不同机型含义不一致 → 热特征采集器按多路径读取并保留来源标记；缺失时使用可解释的备用输入和低置信度。
- 估算模型输出异常 → 融合层做范围、置信度和质控校验；异常结果不允许保存为可复制报告。
- 系统语音识别隐私边界不完全受 App 控制 → 点位识别设为可选能力，并提供手动录入；隐私说明明确区分测量音频和点位语音识别。
- 复制文本格式不符合现场填报习惯 → 复制模板集中在 `CopyTextBuilder`，后续可按目标系统字段顺序调整。
- 用户复制后是否真正提交不可由 App 自动得知 → 首版只记录“已复制”状态，不声称已提交。
- 目标填报系统接口未知 → MVP 暂不对接 API；具体第三方系统适配作为后续扩展。
- Android Studio 模拟器可能不具备真实双麦、气压或完整热特征输入，且本地模拟器可能不可用 → 测试验证可改用 Android Studio 连接真机，重点验证 UI 流程、权限降级、状态流转、本地存储和复制结果；真实传感器精度验证作为后续现场测试。
- 技术方案与截图位于被 `.gitignore` 忽略的 `docs/` 目录 → OpenSpec 文档应沉淀足够的需求结论，避免实现依赖仅存在于本地的参考文件。

## 迁移计划（Migration Plan）

1. 保留当前 `MainActivity` 和 Navigation 框架，替换模板 Fragment 内容为测量主界面和结果确认界面。
2. 增加测量、填报、存储、权限隐私包，并先用本地保存和复制文本跑通端到端流程。
3. 在 `AndroidManifest.xml` 中增加必要的麦克风权限和可选硬件特性声明。
4. 增加本地数据库和加密密钥管理；历史模板数据无需迁移。
5. 增加单元测试覆盖融合、质控、报告状态流转和复制文本生成。
6. 使用 Android Studio 连接真机完成 MVP 主流程验证，覆盖权限授权/拒绝、测量成功/降级、报告保存、历史查看和复制结果。
7. 若变更失败或需要回滚，可回退到模板页面和无持久化状态；MVP 不涉及线上数据迁移。
