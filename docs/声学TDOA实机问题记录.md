# 声学 TDOA 实机问题记录

## 现象

在实机调试中，声学链路可以完成采样、左右声道拆分和 TDOA 计算，但 `sampleOffset` 基本维持在 `0-2` samples。将主路径临时从 JNI/C++ TDOA 切换到 Kotlin 参考实现后，现象仍然存在，因此当前不能简单归因为 native 实现错误。

以小米机型内置麦克风间距 `4.8cm`、采样率 `48kHz` 为例，空气声速范围 `300-380m/s` 下，双麦轴线方向的理论 lag 大约为 `6.1-7.7` samples，常温声速 `343m/s` 下约为 `6.7` samples。实测 `0-2` samples 会反推出异常声速：

| sampleOffset | 反推声速 |
| --- | --- |
| 0 | 无法计算 / 无有效 TDOA |
| 1 | 约 2304m/s |
| 2 | 约 1152m/s |

因此当前代码会将声学路径标记为 `SOUND_SPEED_OUT_OF_RANGE` 或 `TDOA_UNAVAILABLE`，并降级到热特征演示估算。

## 可能原因

- 声源不在双麦轴线方向。TDOA 测到的是两个麦克风到声源的路径差，不等于固定麦距；声源在手机正前方、远场或侧向时，路径差会小于麦距，lag 会变小。
- 双扬声器或多个声源同时发声。左右麦收到的是多个声源叠加，互相关可能选到综合峰或错误峰，导致 offset 偏小或不稳定。
- 环境漫反射较强。普通室内噪声、回声、远场声音会削弱明确的方向性延迟。
- Android 音频链路可能做了降噪、波束形成、自动增益或 stereo downmix，即使请求 `UNPROCESSED` / stereo，也可能拿不到独立双麦原始信号。
- 内置静态机型库的麦距只是技术方案中的演示值，未经过实机标定；如果实际有效麦距不是该值，反推声速也会偏离。

## 当前处理

- 主路径恢复为 JNI/C++ TDOA，Kotlin 实现保留为单元测试参考。
- 当 TDOA 无返回或 `sampleOffset=0` 时，返回 `TDOA_UNAVAILABLE`。
- 当 TDOA 有返回但反推声速超出 `300-380m/s` 时，返回 `SOUND_SPEED_OUT_OF_RANGE`，不再误报为 TDOA 不可用。
- UI 和报告继续展示热特征降级结果，并标注未标定演示估算。
- 代码中保留声学诊断摘要：左右声道 RMS、零延迟相似度、实际 lag、按麦距推算的轴线预期 lag、声速和可能原因提示。

## 后续排查建议

1. 使用单点瞬态声源测试，例如靠近顶部麦或底部麦打响指/轻敲，避免使用手机自身双扬声器同时播放。
2. 观察诊断摘要中的 `左右声道近似相同` 和零延迟相似度。如果相似度长期接近 `1.00`，更偏向系统返回伪 stereo 或强处理后的双声道。
3. 分别测试手机顶部、底部、左侧、右侧近距离声源。如果实际 lag 仍长期保持 `0-2`，说明当前设备/系统音频输入不适合直接按双麦 TDOA 反推声速。
4. 若要继续推进声学链路，需要外部单点声源、校准音频、每机型有效麦距标定，或更明确的设备音频输入能力验证；不能基于当前实测结果声明声学测温精度。
